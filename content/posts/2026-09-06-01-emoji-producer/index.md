## 起因

这个项目起源于我在微信里使用表情包时的一个很具体的感受：静态图片有时已经表达了意思，但如果人物或画面能动起来，表情可能会更有趣。因此我尝试做一个网站，让用户上传一张人物图片，再用文字描述动作、情绪和风格，把它生成成可以使用的动态表情包。

这里的目标是做出一个可运行的工具，不是训练模型，也不是声称模型可以稳定地保留所有人物细节。项目主要使用 Codex 协作完成。

## 当前实现

页面提供了以下输入和控制项：

- 上传主图片；
- 用文字描述动作和风格；
- 填写负面要求；
- 调整动作强度；
- 选择是否尽量保留人物特征；
- 上传可选的参考图片或视频；
- 选择本地演示、DashScope Wan 或 Replicate。

后端由 `server.py` 提供 HTTP 服务。提交生成请求后，服务端创建任务并返回任务编号，前端通过 `/api/jobs/<job_id>` 轮询状态，完成后在页面中预览并下载 GIF。这样处理是为了避免远程视频模型的生成时间超过普通 HTTP 请求的超时限制。

## 主要流程

项目目前包含三条路径：

1. 本地演示路径读取图片，提取主体，生成若干带有运动、背景和文字效果的帧，再合成为 GIF。这条路径不需要远程模型，主要用于本地验证页面和完整交互流程。
2. DashScope 路径把处理后的图片和文字参数提交给 Wan 图生视频接口，取得异步任务编号，轮询任务状态，下载返回的视频，再通过 FFmpeg 转成 GIF。
3. Replicate 路径提交图生视频预测任务，等待结果并下载输出；如果返回的是视频，同样需要转成 GIF。

服务端还处理了图片格式和大小校验、临时输出目录、健康检查、可选密码登录、会话 Cookie、安全响应头和环境变量配置。README 中记录了 Docker、Render 和 Railway 等部署方式，并提醒不要把 `.env`、上传素材和输出视频提交到 Git。

## 交付物

- `index.html`：上传、参数设置、预览和下载界面；
- `app.js`：登录、模型配置读取、生成任务提交和状态轮询；
- `server.py`：本地服务、任务执行、本地演示 GIF、远程模型调用和输出管理；
- `requirements.txt`、`Dockerfile`、`start.ps1`：运行和部署辅助文件；
- `README.md` 和 `.env.example`：本地运行、部署和环境变量说明；
- 公开源码仓库：[Kindseal7/emoji-producer](https://github.com/Kindseal7/emoji-producer)。

## 结果和边界

现在已经有一个可以从上传图片走到 GIF 下载的 Web 工具，并且保留了本地演示和远程模型两种模式。参考素材可以在界面中上传，但从当前代码看，远程 provider 的核心请求仍主要使用主图片和文字参数，不能把“上传参考素材”理解成所有远程模型都已经实现了严格的多参考控制。

远程生成依赖对应的 API Key，生成结果保存在临时磁盘，默认会清理，服务重启后历史结果可能失效。人物身份保持、动作连贯性和画面质量仍取决于模型和输入图片，项目没有对这些效果作稳定性保证。当前记录也没有包含完整的历史对话，因此不能补写未留在代码和 README 中的每一次迭代原因。

## 如何运行

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python server.py
```

然后访问 `http://127.0.0.1:8000`。不配置 `APP_PASSWORD` 时，本地默认不要求登录；接入远程模型时，还需要在环境变量中配置对应密钥。
